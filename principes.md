# Принципы быстрых экспериментов и автономного обучения

Переносимая инструкция для любой архитектуры в этом проекте. Обновлено
16 ноября 2026 года. Конкретные модели, запуски, результаты, параметры runner
и команды ветки хранятся в её журнале архитектуры; для MLP это `MLP.md`.
Прочитать также `AGENTS.md`, `PLAN.md` и текущий код целевой ветки.
Распределение У1/У2 и прежний график отменены владельцем; правила проверки сохраняются.

## Основной принцип

Быстро и локально сравнивать гипотезы с контрольной моделью на одинаковых данных
и сопоставимом бюджете. Увеличивать бюджет перспективным вариантам; полный train
использовать для подтверждения выбранной идеи. Перед запуском проверять журнал:
идентичный завершённый опыт переиспользовать, повторять его только ради измерения
воспроизводимости или проверки нового фактора.

Малый опыт — предварительный фильтр. Медленно обучающаяся модель может раскрыться
позже; сохранять возможность продолжить вариант с улучшающейся кривой.

## Данные и независимая проверка

- Исходный датасет зафиксирован: таблицы, метки, кандидатов и подготовленные
  версии не переписывать. Выборки и кеши создавать отдельно с manifest и хешами.
- Для ранжирования брать целые ленты: сохранять все пары кандидатов и метки.
  Соблюдать общие контракты масок, истории и эмбеддингов из документации данных.
  Не использовать недоступные на инференсе признаки и порядок строк как сигнал.
- Обучать веса и преобразования признаков только на train. Val использовать
  для выбора и проверки; test — для итогового инференса.
- Заранее отделить selection для выбора эпох, гипотез и весов ансамбля от control
  для редкой проверки. Для временной задачи control должен быть более поздним.
  Границу зафиксировать, одинаковые timestamp не разрывать.
- Конкретная пропорция разбиения — настройка протокола, а не требование архитектуры.
  Между сравниваемыми моделями сохранять одни и те же ключи и границу.
- После фиксации модели считать итоговую метрику и прогнозы на всей официальной
  val. Общая метрика включает selection и не считается полностью независимой.
  Регулярный подбор по control лишает его роли отложенной проверки.
- Полный train не означает train+val. Объединение допустимо только как отдельный
  согласованный финальный запуск без заявления о независимой оценке на прежней val.
- Использовать официальный evaluator. Для этой задачи основной показатель —
  полный NDCG с равным весом лент; loss и NDCG@k записывать отдельно.

## Быстрый локальный отбор гипотез

Это целевой протокол: наличие текста не означает, что ступени уже реализованы.
До запуска проверить код и откалибровать бюджет по скорости новой архитектуры.

1. Зафиксировать небольшую вложенную выборку train: исходный ориентир — 0,78%,
   следующий объём — около 1,56%, затем больше по необходимости. Точную долю
   лент брать из manifest. Отдельно зафиксировать до 2 000 целых selection-лент
   с разными датами, длинами истории и числом кандидатов.
2. Один раз подготовить на SSD нужные признаки и векторы. Ключ кеша включает
   хеши входов, схему и параметры преобразований. Кеши разных моделей совместимы
   только при совпадении контрактов; target хранится отдельно.
3. Зафиксировать контроль, seed, порядок батчей, batch size, evaluator и бюджет.
   Разброс контроля оценить несколькими seed на том же стенде.
4. Проверить техническую исправность примерно на 20 батчах: конечные loss и
   градиенты, маски, сохранение/возобновление, корректность ключей и кандидатов.
5. Начать сравнение примерно с 200 optimizer steps. Перспективные варианты
   продолжать до 800 шагов суммарно, сохраняя optimizer и RNG.
6. Для 2–3 лидеров увеличить бюджет, проверить весь selection и второй seed.
   Подтвердить преимущество на следующем объёме train; затем обучать новую
   выбранную гипотезу на полном train.

Числа 20/200/800, размеры выборок и число лидеров — исходные ориентиры,
не гарантия времени или достаточной сходимости для любой архитектуры.
Сопоставлять одинаковые обновления при одинаковом batch size; при его изменении
дополнительно учитывать число обработанных лент. Для методов без optimizer steps
заранее определить сопоставимую единицу ресурса. Время подготовки, обучения,
валидации и память измерять отдельно. Достижение аварийного лимита времени
означает «бюджета недостаточно», а не «архитектура плохая».

## Как принимать решения

Менять один существенный фактор за сравнение; сочетания успешных идей проверять
отдельно. Считать парный прирост NDCG на одинаковых лентах. Оценивать разброс
между seed и bootstrap с учётом повторных пользователей; порог полезного
улучшения выбирать по измеренному шуму контроля.

- Продолжить: выигрыш повторяется или кривая ещё заметно улучшается.
- Остановить: устойчивое отставание при достаточном бюджете.
- Перепроверить: разница мала, меняет знак или модель не успела обучиться.

Проверять срезы по времени, длине истории, числу кандидатов и отсутствию
эмбеддингов. Не переносить результаты между разными объёмами train как будто
это прямое сравнение архитектур. Сохранять место для медленно сходящихся идей.

Не предполагать, что CPU- и GPU-результаты численно идентичны. Конкретные пути
проекта, окружения и output определить для целевой ветки; пароли, ключи и токены
в Markdown и Git не записывать.

- Каждый опыт получает Run-ID, отдельный output, конфигурацию, seed и замороженный
  код/commit с хешами. Для параллельных работ использовать отдельные worktree
  или снимки и совместимые закреплённые окружения.
- Не изменять код и зависимости работающего снимка. Перед запуском проверить
  активные процессы и занятость GPU; чужие задачи не останавливать.
- Проверить доступность выбранного ускорителя, устройство модели и настоящий
  шаг обновления весов. Сообщение «worker started» само по себе этого не доказывает.
- Данные и кеши держать на SSD. Измерять CPU-подготовку, ожидание данных,
  передачу на GPU, время шага, RAM/VRAM и пропускную способность. Число потоков,
  prefetch, pinned memory и batch size подбирать по замерам. Загрузка GPU 100%
  не является самоцелью; важны скорость и качество при доступной памяти.
- На ноутбуке оставлять ресурсы для работы владельца.

## Автономность и восстановление

Обучение должно продолжаться после закрытия чата, CLI или SSH.
На Windows использовать независимую задачу планировщика или проверенный
отсоединённый процесс; на другой ОС — соответствующий менеджер процессов.
Выбирать собственные имена задач и файлы состояния для каждой очереди.
Проверять запуск реальными шагами и логами, а не только успешным созданием задачи.

- Предусмотреть stdout/stderr в файлы, PID, блокировку второго контроллера
  и защиту от запуска дублирующего тренера после разрыва связи.
- Сервер не выключать и не перезагружать: включение может занимать около 30 минут.
  Поддерживать предотвращение сна. Это не защищает от физической потери питания.
- Атомарно сохранять checkpoint каждые несколько минут и на границах этапов:
  модель, optimizer/scheduler при наличии, RNG, эпоху/курсор, использованный бюджет,
  лучшую метрику и fingerprint данных/разбиения.
- Возобновление того же опыта должно сохранять состояние и бюджет.
  Загрузка только весов — новый опыт; отражать это в журнале.
- После разрыва сначала проверять живые процессы. По указанию владельца
  останавливать через сохранение checkpoint; команды остановки уточнять в
  реализации целевой ветки.
- После подтверждения реальных шагов всех разрешённых очередей дать статус
  и команды проверки, затем закончить работу. Не ждать окончания без отдельной
  просьбы владельца.

## Понятные логи

Сразу показывать архитектуру и Run-ID, CPU/GPU, объём данных, стадию,
эпоху/шаг, завершённые варианты, лучшую метрику и ошибки. Записывать скорость,
время подготовки/train/val, ожидание данных и потребление RAM/VRAM.

Режим `--logs` должен разово выводить полный читаемый отчёт, начиная с ошибки
и traceback при их наличии, включая логи контроллера. Без обрезки панелью
и необходимости Ctrl+C. Повторные снимки — явный `--watch`, машинный формат —
`--json`. Конкретные команды мониторинга хранить в журнале архитектуры.

Различать завершение эпохи, одного опыта и всей очереди. Завершение подтверждать
итоговым статусом и отчётом; отсутствие ошибки в хвосте лога этого не доказывает.

## Результаты, повторное использование и ансамбли

Вести подробный `experiments.md` и короткий журнал выбранной архитектуры.
Там же хранить её особенности, команды, пути, ограничения и ошибки реализации.
Для каждого опыта записывать простое описание, Run-ID, статус, данные, устройство,
seed, фактические шаги/эпохи, частичность, метрики, время, память и решение.
Selection, control, полный val и сайт указывать раздельно; неизвестное — `—`.
Сохранять неудачные опыты и причины; score владельца помечать как его сообщение.

Перед повтором сверять архитектуру, признаки/кеш, manifest, split, seed,
optimizer/loss, batch size, learning rate, бюджет и начальные веса.
Повтор без нового фактора допустим для явно обозначенной проверки воспроизводимости.

Для ансамбля получать прогнозы на всей официальной val из зафиксированной модели,
соединять по `feed_id` и `item_id`, а не по порядку строк. Проверять schema,
точное покрытие, уникальность, отсутствие null/NaN/Inf. Сохранять Run-ID,
выбранную эпоху/итерацию, SHA-256 модели и файла, commit/хеш кода, границу split
и полную метрику. Не путать экспорт val с прогнозом test. Веса ансамбля подбирать
на selection, проверять на control.

## Порядок работы нового чата

1. Прочитать инструкции целевой ветки, общий протокол и журнал её архитектуры;
   проверить входы, окружение, активные процессы и последние отчёты.
2. Найти существующие эквивалентные опыты; определить одну гипотезу и контроль.
3. Реализовать чистый код, выполнить подходящие проверки, откалибровать скорость
   и подготовить изолированный запуск.
4. Запустить разрешённые очереди, подтвердить реальные шаги, дать команды статуса
   и закончить ожидание. По следующему запросу собрать результаты и обновить журнал.

Работать в ветке, указанной владельцем; `main` не менять. Соблюдать правила
публикации целевой ветки, не публиковать секреты, датасеты и веса.
Подготовка артефакта не разрешает отправку на сайт соревнования: требуется прямое
указание владельца. Перенос этого файла сам по себе не разрешает запуск,
остановку чужих задач, push или отправку.
