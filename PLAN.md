# План работы команды из двух человек

Подготовлен 15 ноября 2026 года. Участники обозначены как У1 и У2 до назначения имён. Каждый работает со своим AI-ассистентом; оба пишут код, обучают модели и анализируют результаты. Разделение ниже задаёт ответственность за инфраструктуру и вопросы исследования, но не закрепляет методы нейросетей.

## Что решаем

Для готовых кандидатов каждой ленты `feed_id` предсказываем `score`, чтобы выше оказались объявления с бинарным `target=1`. Искать кандидатов заново не требуется. Оценки сравниваются внутри ленты. Train, val и test разделены по времени; Public/Private — примерно 30/70 по времени тестовых лент. Отправка: Parquet с `feed_id:int32`, `item_id:int32`, `score:float32`, точным покрытием пар шаблона и конечными оценками. [Описание задачи](https://ods.ai/competitions/avitotechrecsys2026).

Используем числовые признаки, категории, эмбеддинги и историю. История идёт от новых событий к старым и может быть пустой. Таблицы эмбеддингов отдельные для каждого split; индекс `-1` означает отсутствие вектора, а операции над `int8` требуют перевода в float. Поле `pos` доступно только в train; порядок кандидатов val/test не является признаком позиции. [Описание данных](https://ods.ai/competitions/avitotechrecsys2026/dataset).

Основная локальная метрика — NDCG по всей ленте с равным весом лент. В просмотренном `calculate_metrics.py` из [официального архива](https://storage.yandexcloud.net/avitotech-mlcup-2026/baseline.zip) `ndcg` использует cutoff=None; @10 и @30 считаются отдельно. При равных оценках отрицательная метка идёт первой, при отсутствии положительных меток NDCG=1. На странице есть неоднозначное упоминание `IDCG@30`: перед финалом сверить актуальную версию оценивания, не заменять основной NDCG на @30 самостоятельно.

## Как выбираем и проверяем подходы

1. Начать с общего воспроизводимого опорного решения. Официальные бейзлайны можно использовать для проверки пайплайна и как ориентир; ни один из них не объявляется финальным методом.
2. Для любого подходящего подхода записать ожидаемый эффект, нужные сигналы и бюджет. Допустимы разные нейросетевые архитектуры, функции потерь, способы обработки истории и сочетания моделей; простые контрольные решения помогают оценивать реальный выигрыш.
3. Первый запуск — короткая проверка на фиксированной подвыборке. Положительный результат подтвердить на полном согласованном протоколе; результаты разных объёмов не сравнивать напрямую.
4. В одном сравнении менять один существенный фактор. Если изменений несколько, затем проверить вклад каждого отдельно.
5. Лидеров повторять с несколькими seed в пределах бюджета. Считать парную разницу NDCG на тех же лентах; при необходимости оценивать неопределённость, учитывая повторных пользователей. Порог практического улучшения определить после измерения разброса опорного решения.
6. Проверять качество по дням, длине истории, числу кандидатов, наличию эмбеддингов и новым/известным объектам. Фиксировать общее качество вместе с деградациями на срезах.
7. Проверять сочетания моделей только по сохранённым прогнозам на одних и тех же ключах val. Веса выбирать на заранее выделенной части val, проверять на отложенной части; не подбирать их по Public.

## Единый протокол

- У2 фиксирует версию evaluator; У1 проверяет на ручных примерах идеальный/обратный порядок, равные score, ленты без положительных меток и разный размер групп. Это необходимые проверки корректности, а не модельные гипотезы.
- Использовать готовую val как основной ориентир. До серии поисков выделить её более позднюю часть для редких контрольных проверок, сохраняя целые ленты и одинаковые timestamp вместе; зафиксировать границу и размеры. Полный val оценивать у лидеров с пометкой, что он уже участвовал в выборе.
- Случайное разбиение строк не использовать как замену временной проверке. Маски, нормализацию, словари и агрегаты обучать без val/test-меток; target не включать во входы. Для агрегатов train использовать прошлое или out-of-fold схему.
- `pos` исследовать только как отдельную гипотезу об обучении и смещении показов. Не требовать этот признак на инференсе и не восстанавливать его из случайного порядка val/test.
- Перестановка кандидатов вместе с их признаками не должна менять оценки соответствующих объявлений, кроме допустимой численной погрешности. Проверить это отдельно для моделей с контекстом ленты.
- Хранить конфиг, seed, версию данных/разбиения, код, окружение, логи, предсказания и контрольные суммы артефактов. На запуск записывать время обучения, инференса и пиковую память.
- После закрытия выбора модели решить отдельно, нужно ли дообучение на train+val. Такой запуск больше не имеет независимой оценки на прежнем val: не приписывать ему метрику предыдущего checkpoint.

## Ежедневная координация и GitHub

- В начале дня: коротко сверить итоги, выбрать каждому следующий опыт, согласовать очередь вычислений и владельца каждого общего файла.
- Перед запуском: создать карточку в журнале соответствующей модели (для CatBoost — `catboost_exp.md`), занять уникальный для проекта ID, указать бюджет. Ссылки на журналы и общий шаблон находятся в `experiments.md`. После запуска: добавить факты, сбои, решение и следующий шаг. Неудачные идеи сохранять.
- Для Public использовать только осмысленные проверки; вести общий счётчик 5 попыток команды. Необязательно расходовать весь лимит. Решение о продвижении основывать прежде всего на локальной проверке.
- Работать в отдельных локальных ветках, например `u1/exp-001` и `u2/exp-002`. Изменения общей инфраструктуры согласовывать до длинных запусков; второму участнику проверять diff и воспроизводимость.
- Перед каждой отправкой изменений в GitHub показать владельцу список файлов, diff, результаты проверок и ограничения. Push и любые записи через GitHub API выполнять только после его явного одобрения конкретных изменений. До одобрения всё остаётся локально.

## Первые конкретные задачи

- **У1:** инвентаризация ресурсов и данных → загрузчик целых лент → аудит масок/индексов → опорное обучение → EXP-001 и EXP-002.
- **У2:** проверка метрики → валидатор сабмита → общий отчёт срезов → воспроизведение опорного обучения → EXP-003 и EXP-004.
- **Вместе:** подтвердить протокол, бюджеты и состав команды; после первых результатов перераспределять остальные гипотезы по ожидаемой пользе и доступности ресурсов.
